# malware_gen_framework — Codebase Summary

## Purpose
End-to-end pipeline that takes a target environment spec (YAML) and generates undetectable malware source code, optionally verifying it inside an ephemeral QEMU VM and retrying until EDR/AV detection is evaded.

## Entry Point
`python -m malware_gen_framework <command> --spec target.yaml`

Subcommands: `generate` (code only, no VM), `verify` (VM only), `run` (full pipeline), `analyze` (DB context dump, no generation).

## Pipeline Phases (pipeline.py → MalwarePipeline)

### Phase 0 — Spec Parsing (spec_parser.py + target_spec.py)
- Reads YAML/JSON spec into Pydantic `TargetEnvironmentSpec`
- Fields: `os_platform` (linux/windows/macos), `os_version`, `edrs` (list), `antivirus`, `patch_level`, `installed_compilers`, `common_tools`, `domain_joined`, `admin_rights`, `sandbox_detectors`, `custom_gates`, `malware_type` (freeform: "info stealer", "ransomware", etc.)
- Auto-completes missing fields (e.g., infers platform from os_version string, defaults compilers to gcc/python3)

### Phase 1 — DB Query & Context Assembly (db_query_engine.py → context_builder.py → prompt_templates.py)
- `DBQueryEngine` queries 3 external corpora via subprocess:
  - `/home/kei/llm_vault/malware_corpus/query_malware.py` → `MalwareTechnique` objects
  - `/home/kei/llm_vault/malware_corpus/query_poc.py` → `PoC` objects
  - `/home/kei/llm_vault/hermes_qwen_cti/query_rag.py` → `CTIFinding` objects
- `ContextBuilder` deduplicates and ranks results:
  - Techniques ranked by detection_rating + EDR-match boost + category bonus
  - PoCs ranked by severity (critical/high/medium/low) + exploit type (RCE/PRIVESC highest)
- Produces `ContextBlock` with `context_hash` (SHA-256 of ranked IDs, used for stuck-detection)
- `EvasionSelector` + `ExploitSelector` further filter results per EDR stack / OS version

### Phase 2 — LLM Generation (generation_engine.py + prompt_templates.py)
- `GenerationEngine` orchestrates: DB query → context → evasion/exploit selection → compiler prompt → full generation prompt → LLM call
- `SubprocessLLMClient` supports two backends:
  - Local: `llama-cli` (llama.cpp) with GGUF model from `~/.llm_vault/models/`
  - HTTP: LM Studio / OpenAI-compatible API at `http://localhost:1234` (default model: `qwen3.6-35b-a3b-uncensored-hauhaucs-aggressiv`)
  - Retries up to 3x with doubling token limit on truncated output; validates completeness by checking balanced braces/parens
- Jinja2 `GENERATE_MALWARE_TEMPLATE` injects ranked techniques, PoCs, CTI findings, compiler instructions, and `malware_type` description
- LLM is instructed to return raw C source with inline build comments, no markdown wrapper
- Output: `GenerationResult(source_code, build_instructions, context_hash, prompt_length)`

### Phase 3 — VM Provisioning (provision_engine.py + linux_provisioner.py + windows_provisioner.py + image_sources.py)
- `ProvisionEngine` pipeline: ensure base image → COW qcow2 snapshot → auto-provisioning ISO → boot QEMU → wait for SSH
- Linux: cloud-init YAML ISO; Windows: autounattend XML ISO
- `QEMUProcess`: `qemu-system-x86_64` with KVM, OVMF UEFI, virtio-net user NAT (SSH forwarded to port 10022), QMP socket
- `VMInstance.execute_command()` runs commands via asyncssh
- VM credentials: `vmuser` / `vmuser123`, SSH port 10022

### Phase 4 — Verification (verifier.py)
- `Verifier.verify()`: write source → compile → execute → check EDR logs → behaviour checks → sandbox check
- Compile command built from compiler_instructions or fallback: `gcc -O2 -Wall` (Linux) / `x86_64-w64-mingw32-gcc` (Windows)
- EDR detection: queries `/var/log/syslog` / `audit.log` (Linux) or WinEvent (Windows)
- Behaviour checks: binary exists/executes, network activity (ss), window creation
- Sandbox checks: CPU count < 2, RAM < 1000MB → flags as sandbox
- Returns `VerificationResult` with `DetectionLevel` (NONE/LOW/MEDIUM/HIGH), `alerts: List[AlertRecord]`, `behaviour_checks`

### Phase 5 — Retry Loop (loop_controller.py)
- `LoopController.run_loop()`: iterates generate → verify up to `max_iterations` (default 5)
- Failure classification: `COMPILATION_FAILED`, `EXECUTION_CRASHED`, `DETECTED`, `SANDBOX_DETECTED`, `CONTEXT_STUCK`, `LLM_GENERATION_EMPTY`
- Stuck detection: if `context_hash` unchanged for `stick_threshold` (default 2) consecutive iterations, forces new variant seed
- Exponential backoff between retries: base=1s, max=30s
- Stops early on `detection_score == "none"` (success)
- Variant generation: appends `/* VARIANT SEED: iter_N */` to prior source and regenerates
- Returns `LoopResult(iterations, best_result, total_iterations, success)`

## Data Models (db_models.py)
- `MalwareTechnique(id, name, description, category, os_type, edr_detection, detection_rating, references)`
- `PoC(id, cve, title, description, exploit_type, target_os, severity, source, code, references)`
- `CTIFinding(id, title, description, severity, threat_actor, indicators, related_cves, references)`
- `QueryResult(malware_techniques, poc_results, cti_findings)`

## Config Models (config_models.py)
- `TargetOS` enum: UBUNTU_24_04, UBUNTU_22_04, WINDOWS_11, WINDOWS_10
- `VMProvisionConfig`: os_type, base_img, cow_img, vm_name, cpu_cores (4), ram_mb (8192), ssh_port (10022), username, password, ssh_key, enable_ssh, skip_tpm

## Supporting Modules
- `debug_logger.py`: `DebugLogger` — step-by-step trace with phase markers; activated via `--debug` CLI flag
- `image_sources.py`: ensures base OS images exist (download/verify)
- `linux_provisioner.py`: generates cloud-init YAML + ISO creation
- `windows_provisioner.py`: generates autounattend XML + ISO creation
- `compiler_selector.py`: utility for selecting compiler flags per platform

## External Dependencies
- Three separate corpora at `/home/kei/llm_vault/`: `malware_corpus/` (techniques + PoCs), `hermes_qwen_cti/` (CTI RAG)
- LLM: local llama.cpp GGUF model or LM Studio HTTP API (localhost:1234)
- QEMU/KVM for VM provisioning; asyncssh for SSH bridge; jinja2 for templates; pydantic for spec models; PyYAML for spec parsing

## Spec File Format (target.yaml / linux_spec.yaml)
Key fields: `os_platform`, `os_version`, `malware_type`, `edrs`, `antivirus`, `patch_level`, `installed_compilers`, `common_tools`, `domain_joined`, `admin_rights`, `sandbox_detectors`, `custom_gates`, `notes`

## Output Files
Generated to `--output` dir (default `results/`):
- `malware_source.c` — generated malware source code
- `pipeline_report.txt` — pipeline report (target, generation stats, VM status, loop summary)
