01 Architecture Overview ▶

Three execution paths exist, each building on the one below it. The chunk assembler is the production engine; the LLM pipeline is legacy/experimental; Hermes orchestrates either autonomously.

Recipe YAML → Chunk Assembler → Template Substitution → API Rewrite → MinGW / Zig → Resource + Rich Header → PE / DLL / CPL / JScript
Hermes LLM → Tool Calls → Assembler → Deploy (SSH) → Analyze → Adapt / Mutate

Pipeline Comparison

02 Chunk Assembler Pipeline ▶

The assembler reads a YAML recipe, resolves chunk dependencies via topological sort, concatenates into a single compilable source file, applies API rewriting, and compiles with MinGW or Zig.

Recipe Format

Each recipe is a YAML file specifying which chunks to include. The assembler resolves depends: metadata from chunk headers and orders chunks correctly.

FieldTypePurpose
api_resolvestringHash-based API resolver (DJB2, CRC32, FNV1a, ROR13, PEB walk)
evasionlistEvasion chunks to include
processstringProcess manipulation (PPID spoof, ghosting, masquerade)
corelistBuffer management, command exec, file I/O
collectorslistData collectors (sysinfo, browser, clipboard, etc.)
exfilstringExfiltration method (TCP, HTTP, DNS, file drop)
archstringEntry point architecture (main, DllMain, CplApplet, shellcode)
resourcesboolInject resource section + manifest (REQUIRED for CS PE evasion)
varsdictTemplate variables (C2_IP, C2_PORT, etc.)

Assembly Pipeline Stages

#StageWhat It Does
1Parse recipeRead YAML, detect output format (C/JScript/VBScript/Batch)
2Variant randomizationIf --randomize: swap chunks with alternatives from the same variant group
3Dependency resolutionParse depends: metadata from chunk headers, topological sort
4Header collectionDeduplicate headers: across all chunks; winsock2.h always first
5Body concatenationRead each chunk body, inline local #includes, strip include guards
6Template substitutionReplace {{COLLECTOR_CALLS}}, {{EVASION_INIT}}, {{C2_IP}}, etc.
7API rewritingIf api_resolve set: replace static API calls with hash-resolved lookups
8ObfuscationOptional string encryption, control flow flattening via obfuscate.py
9CompilationMinGW or Zig cross-compiler → PE/DLL/CPL
10Post-compileResource injection, Rich header spoof, PE timestamp stomp, checksum fix

Post-Compilation Transforms

Resource Injection — Embeds a version info resource from 50 legitimate app profiles (AppLocker, Update Orchestrator, etc.) plus an application manifest. Resource section presence makes PE look like a real application to ML classifiers.

Rich Header Injection — Fabricates a Rich/DanS header matching MSVC 14.x toolchain signatures. Defeats toolchain fingerprinting that flags MinGW-produced binaries.

PE Timestamp Stomping — Overwrites TimeDateStamp with a plausible older date. Defeats "recently compiled" heuristics.

Compilers — MinGW (default, proven) produces standard PE. Zig CC produces binaries with different linker signatures and section layout, diversifying the static surface. Both target x86_64-windows.

04 Hermes AI Orchestrator ▶

Hermes is an autonomous campaign engine powered by a local LLM (Qwen 35B on Blackwell GPU, port 11235). It operates via a tool-use loop: the LLM receives a system prompt with target context, reasons about next steps, and calls tools to execute them.

System Prompt → LLM Reasoning → Tool Call → Tool Result → LLM Reasoning → Loop

Operating Modes

ModeLLMPurpose

validateNoMechanically test all PASS recipes against target EDR. Output: validation report with pass/fail/detection details.
evadeYesLLM-driven mutation loop on specific recipes until they evade. Changes one dimension at a time.

Intelligence Systems

Strategy Tree — Decision tree per EDR with proven techniques, fallback paths, and format preferences. Guides the LLM toward approaches that have worked before.

Knowledge DB — Persisted at hermes_knowledge.json. Records every operation: recipe, evasion layers, EDR, result, C2 bytes, failure type. Queried by the LLM to avoid repeating failed approaches.

Innovation Engine — After N consecutive failures (configurable, default 100), enters innovation mode: gives the LLM write access to scratch files and a focused prompt to try experimental techniques outside the recipe system.

Circuit Breaker — After 5 consecutive VM-unreachable errors, aborts the campaign. Prevents infinite loops when infrastructure fails.

06 Design Rationale & Trade-offs ▶

Key Design Decisions

Chunks vs Pure LLM Chunk templates are deterministic and testable — the same recipe always produces the same binary (minus randomization). Pure LLM generation is creative but unreliable: it misses MinGW constraints, introduces compilation errors, and can't be batch-tested. The chunk system handles the 90% that's formulaic; Hermes adds LLM creativity for the 10% that requires adaptation.
YAML vs Code API Recipes are YAML because Hermes (the LLM) can read and write them. A Python API would require the LLM to write Python code, which is error-prone. YAML is the interface contract between the AI orchestrator and the deterministic assembler.
Variant Groups vs Parametric Variant groups give controlled polymorphism: every variant in a group has been manually written and tested for compilation. Parametric generation (e.g., "generate N random evasion functions") produces untested code. Variant groups are the middle ground between no diversity and chaos.
MinGW vs MSVC The framework runs on Linux. MinGW cross-compiles to Windows PE from the Linux host without a Windows build environment. MSVC requires a Windows machine or complex Wine setup. Trade-off: MinGW produces PE binaries with identifiable default section names and Rich headers — countered by Rich header injection and section renaming post-compile.
Local LLM vs Cloud Local Qwen 35B on Blackwell GPU means no API costs, no content filtering, and no rate limits. Trade-off: single-request bottleneck (no concurrent pipelines), lower reasoning quality than frontier cloud models. Hermes compensates with extensive tool-use and structured prompting.

Strengths & Limitations

STRENGTHS

• Deterministic, testable output from recipes

• ~2M detection-distinct variant combinations

• 4 output formats (PE, DLL, CPL, JScript)

• Autonomous campaigns via Hermes AI

• Self-testing validation loop with VM

• No cloud dependency — fully local

LIMITATIONS

• Chunk compatibility matrix is complex (not all combos compile)

• MinGW PE fingerprint requires Rich header injection to mask

• No EV code signing capability

• Local LLM bottleneck (one pipeline at a time)

• BYOVD / kernel-level attacks not implemented

• Shellcode pipeline is nascent
